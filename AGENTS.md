# Правила работы с проектом FitAgent

## Главное правило — обязательно без исключений

Это правило имеет наивысший приоритет среди правил проекта; отступать от него нельзя.
Если что-либо непонятно, остановитесь и спросите пользователя до продолжения работы:
кратко и лаконично опишите, что именно вызывает сомнения, и предложите варианты решения
для согласования. Не делайте собственных допущений, не додумывайте требования
и не придумывайте обходные решения или «костыли» вместо уточнения.

## Описание проекта

FitAgent — CLI-инструмент для контроля питания пользователя. Пользователь
взаимодействует с приложением через текстовый интерфейс в терминале (TUI).

- **Бекенд:** Python. Бизнес-логика и обработка данных реализуются на Python.
- **Интерфейс:** TUI (Text User Interface), работающий непосредственно в терминале.
- **Команда запуска:** `fitagent`.

Это целевые требования проекта. Реализация приложения и конфигурация запуска ещё не добавлены.
Конкретные библиотеки для TUI, хранения данных и тестирования пока не определены.
Не описывайте запланированные возможности как уже реализованные.

## Архитектура и реализация

- Отделяйте бизнес-логику контроля питания от TUI и работы с хранилищем данных.
- Не размещайте бизнес-логику в обработчиках интерфейса, если её можно вынести
  в независимо тестируемый компонент.
- Сохраняйте `fitagent` как пользовательскую точку входа при изменении структуры проекта.
- Следуйте существующей структуре, стилю и соглашениям проекта. Новые зависимости
  добавляйте только при необходимости; существенные архитектурные решения
  согласовывайте с пользователем.

## Ошибки для пользователя

- Все сообщения об ошибках, видимые пользователю в TUI и CLI, должны быть
  на русском языке и понятны без знания Python или внутренних механизмов приложения.
- Кратко объясняйте, что произошло и что пользователь может сделать дальше.
  Для ошибок формы указывайте поле и ожидаемый формат или допустимый диапазон.
- Не показывайте пользователю необработанные тексты исключений библиотек,
  английские технические сообщения и traceback. Преобразуйте их в понятные сообщения;
  ключи API и персональные данные не должны попадать в сообщения или технические логи.
- Проверяйте пустые поля и неверный ввод до преобразования и отправки в API.
  Добавляйте тесты на понятность сообщений при изменении обработки ошибок.

## Линтер и форматирование

- Форматирование и базовые проверки Python определяет Ruff в `pyproject.toml`,
  а не ручные правила оформления в инструкциях агента.
- Установка: `python3 -m venv .venv`, затем
  `.venv/bin/python3 -m pip install -r requirements-dev.txt`.
- Единая команда проверки: `.venv/bin/python3 scripts/lint.py`.
- Исправление оформления: `.venv/bin/python3 -m ruff check --fix .` и
  `.venv/bin/python3 -m ruff format .`. После исправлений повторите полную проверку.
- `scripts/lint.py` запускает Ruff и проверяет классы и их документацию:
  **до 600 строк — OK; 601–800 — допустимое предупреждение; больше 800 — ошибка**.
- В лимит входят все строки определения класса: заголовок, методы, docstring,
  комментарии и пустые строки внутри него, а также декораторы.
- При приближении к 600 строкам разделяйте обязанности класса на небольшие компоненты.
  Не обходите ограничение за счёт уплотнения кода или ухудшения читаемости.
- Правило применяется ко всем классам проекта, включая тестовые.

## Post-hook OpenCode

- Локальный плагин `.opencode/plugins/fitagent-lint/index.ts` для OpenCode V2
  автоматически запускает линтер после каждого инструмента, включая shell.
- Результат передаётся агенту через обновляемый контекст `fitagent.lint`.
- По умолчанию используется `.venv/bin/python3`, если он существует, иначе `python3`.
  Переменная `FITAGENT_PYTHON` позволяет указать другой интерпретатор с Ruff.
- При `LINT FAILED` агент обязан исправить нарушения и повторить проверку.
  Задача считается выполненной только при `LINT OK` на текущем состоянии файлов.
  Предупреждения для 601–800 строк не блокируют успешный результат.
- Отсутствие Ruff, тайм-аут или ошибка запуска считаются провалом, а не успехом.
- **Ограничение API:** документированный API OpenCode V2 не предоставляет
  блокирующего Stop-хука. Этот post-hook даёт обратную связь на следующем шаге,
  но технически не запрещает отправку финального ответа. Не называйте его
  гарантированной блокировкой завершения агента.

## Документация классов

- Для **каждого класса** создавайте отдельный Markdown-файл рядом с Python-файлом,
  в той же директории. Имя документа: `<ClassName>.md`.
- Имена классов в одной директории должны позволять однозначно сопоставить класс
  с его документом; не допускайте конфликтов имён Markdown-файлов.
- Объём каждого документа — **не более 100 строк**, включая заголовки и метаданные.
- Кратко объясняйте, **что делает класс и зачем он нужен**. Укажите исходный файл,
  основные обязанности и, при необходимости, важные зависимости или ограничения.
- При **любом изменении класса** актуализируйте его Markdown-документацию
  в рамках той же задачи, даже если публичный интерфейс не изменился.
- Всегда указывайте **дату последнего изменения** в формате `YYYY-MM-DD`
  и **версию документа** в формате `MAJOR.MINOR.PATCH`.
- Для нового документа используйте версию `0.1.0`. При последующих изменениях
  увеличивайте как минимум PATCH. Версия документа не означает версию приложения.
- При переименовании или перемещении класса обновляйте имя, расположение и ссылки
  в его документе. При удалении класса удаляйте относящийся к нему документ,
  предварительно убедившись, что он не описывает другие сущности.
- Docstring в коде может дополнять документацию, но не заменяет Markdown-файл.

### Шаблон документа класса

```markdown
# ClassName

- Исходный файл: `module.py`
- Версия документа: 0.1.0
- Дата изменения: YYYY-MM-DD

## Назначение
Что делает класс и зачем он нужен в проекте.

## Основные обязанности
- Ключевые действия и границы ответственности.

## Особенности
Важные зависимости, ограничения или примечания к использованию, если они есть.
```

## Порядок внесения изменений

1. Изучите затрагиваемый код и документацию перед редактированием.
2. Вносите только изменения, необходимые для задачи; не перезаписывайте чужую работу.
3. Добавляйте или обновляйте тесты при изменении поведения приложения.
4. Актуализируйте документы всех изменённых классов, их даты и версии.
5. Запустите `.venv/bin/python3 scripts/lint.py` и добейтесь `LINT OK`.
   Проверка документации контролирует размер, заголовки, исходный файл, формат версии
   и корректность даты; смысловую актуальность и увеличение версии проверяйте вручную.
6. Запустите `.venv/bin/python3 -m unittest discover -s tests -v` и другие доступные
   тесты проекта. Не заявляйте об успешной проверке без запуска.
7. При изменении точки входа проверьте запуск командой `fitagent`.
8. В итоговом сообщении кратко перечислите изменения, выполненные проверки
   и известные ограничения.

Если требования неоднозначны и выбор влияет на поведение приложения или
архитектуру, задайте пользователю уточняющий вопрос до реализации.
